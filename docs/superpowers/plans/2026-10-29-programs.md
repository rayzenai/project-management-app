# Programs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add programs: a named collection of projects with one program manager, who can do on every project in the program what its own project manager can, plus a program page that rolls them up.

**Architecture:** One new table (`programs`) and a nullable `projects.program_id`. Every permission still goes through `App\Support\WorkspaceAccess`; the program manager is added as one more way through the existing checks (never as a team leader), so screens that read `can_*` flags pick it up without change. The program page reuses `App\Queries\ProgressReport`, like the project progress page.

**Tech Stack:** Laravel 13, PHP 8.5, Inertia + Svelte 5 (runes), Pest, PHPStan level 7, Postgres (jsonb rules), Sanctum API.

**Spec:** `docs/superpowers/specs/2026-10-29-programs-design.md`

## Global Constraints

- Git phase 1 is committed (`e1da6b5`) and builds on the same files (`WorkspaceAccess`, routes, `Project`, Guide, `types.ts`): edit around its code, never rewrite it. Stage only this plan's files in every commit; never `git add -A`.
- Every role decision goes through `WorkspaceAccess`; never re-implement one inline. `canViewProject` and `Project::scopeVisibleTo` stay twins, as do `canViewProjectCode` and `Project::scopeCodeVisibleTo`.
- Pattern per feature: Service (returns `ServiceResult`) + FormRequest (authorization in `authorize()`) + JsonResource (`$wrap = null`, ISO-8601 dates), a thin method in **both** `Workspace\` and `Api\` controllers, a route in **both** `routes/web.php` and `routes/api.php`.
- Audit trail only through observers + `ProjectActivityRecorder`. Notifications are in-app (`database`), synchronous, built with `Concerns\BuildsWorkspaceNotification`, never sent to the person who acted.
- Slugs in routes (`{program:slug}`), never numeric ids.
- UI: semantic utilities only, no `dark:`, no raw palette colours, no em-dashes in copy, Lucide icons only, no `rounded-xl`/`shadow-*` outside `.popover`.
- Hint copy, verbatim: under the program manager picker "In a ministry, usually a Joint Secretary."; under the project manager picker "In a ministry, usually an Under Secretary."; by the office admin switch "In a ministry: the Minister, Secretary and Secretariat."
- An organization with no programs behaves exactly as today: the existing suite passes unchanged except tests that list every shared prop or resource key.
- Per task: `vendor/bin/pint --dirty` on your files only (it also formats other uncommitted files; check `git status`), `composer types:check`, the task's Pest files; frontend tasks also `npm run lint:check && npm run format:check && npm run types:check`.

## Review Focus

1. **A project moved from program A to program B**: A's manager loses it at once, B's gains it, and its activity says "Moved from A to B". Test in Task 4.
2. **An office admin posts another organization's `organization_id`** when creating a program: the program is still created in the admin's own organization (or refused for a manager from elsewhere). Test in Task 3.
3. **Archived projects in a program**: the program page leaves them out of its rows and its report, as the Projects page does by default. Test in Task 5.
4. **One person with two hats**: they manage the program and are also the manager of one of its projects. They appear once on the program page, with the role `leader`. Test in Task 5.
5. **An empty program**: the program page renders with no projects and no tasks. Test in Task 5.
